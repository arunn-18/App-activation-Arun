# Production coverage of the v2.6.1 supported surface

**Date:** 2026-08-09 · **Source:** 90-day prod dump (sync triggers), same cleaning as
the eval-set mining pipeline · **Script:** `build/coverage.py` (stdlib-only, reproducible)
· All numbers are aggregates; no tenant values appear here.

## Headline

**Pilot-scope view (added 2026-08-09, after the scope decision):** AI-based automation
building belongs to a separate team's project; this project's charter is the non-AI
surface. Of the **3,710 non-AI organic automations**, the pilot surface fully builds
**3,422 = 92.2%**. The 182 AI-step automations (4.7% of the total) are the sister
project's territory; the engine's gated ai_extract support covered 152 of them.

Original full-pool view — of the **3,892 organic automations** (active, non-demo,
non-migrated) built by **686 tenants** in the 90-day window:

| view | covered |
|---|---|
| **Automations fully buildable by the copilot today** | **3,574 / 3,892 = 91.8%** |
| Tenants whose every automation is buildable | 565 / 686 = 82.4% |
| Distinct structural signatures (trigger + property.op set + action types) | 817 / 1,039 = 78.6% |

"Fully buildable" = trigger, every condition property + operator, every AI variable
type, and every action type sit inside `engine/schema.py`. One unsupported element
anywhere disqualifies the whole automation, so this is the strict count.

The structure-level number (78.6%) is lower than the automation-level one because the
head of the distribution repeats: the same keyword-tag/sender-route shapes account for
a large share of what admins build. Both numbers are honest; they answer different
questions ("how much admin activity could the copilot have handled" vs "how much of
the vocabulary space is covered").

## What blocks the remaining 318 (8.2%)

| blocker | automations touched | sole blocker |
|---|---|---|
| custom fields (conditions or actions) | 95 | 85 |
| `is_present_in` / `contains_any_value_from` operators¹ | ~138 across from/to/domains/subject | ~64 |
| connectors (Salesforce, HubSpot, ClickUp, HTTP…) | 33 | 25 |
| `time_slot` / timezone payloads on date-time conditions | 33 | 32 |
| conditions on `tags` (current tag state) | 24 | 17 |
| approval flows | 10 | 7 |
| `add_followers` action | 10 | 5 |
| conditions on `assignee` | 8 | 5 |
| AI `multi_select` variable type | 6 | 3 |

¹ membership tests against a saved list — a different beast from adding an operator:
the rule references a list *entity* that lives in the workspace, so supporting it
properly needs entity resolution for lists (the workspace.py pattern already fits).

## Implications

1. **The pitch sentence**: the copilot can already build ~92% of everything Hiver
   admins actually created in the last 90 days, verified rule-by-rule against the
   production dump, with measured accuracy on top of it (core 37/40, mt 12/12,
   entity 10/10).
2. **The next surface, by demand, is NOT connectors** — it's the saved-list operators
   and custom fields. Connectors are prominent in roadmap conversations but block
   only 33 automations (0.8%).
3. Everything past 97% is tail; the honest scope recommendation for a pilot is the
   current surface + saved-list ops + custom fields.
